# Phase 3 — Streaming UTF-8 decoder and parser table generator

- Status: completed
- Date: 2026-09-05
- Scope: the first incomplete Phase 3 roadmap item
- Related: `ROADMAP.md` Phase 3; `FEATURE_MATRIX.md` PAR-01, PAR-02,
  PAR-05, QA-01, SEC-01, PERF-01; `docs/phase0/DT-010-parser-corpus-snapshot.md`

## Purpose and background

Establish the Dart-only, renderer-independent byte-processing foundation for the
Phase 3 VT core. The product implementation needs a chunk-independent streaming
UTF-8 decoder and a reproducible generated byte-class/state transition table
that the following C0/ESC/CSI/OSC/DCS/APC parser task can consume.

Phase 0 proved that a no-per-byte-object Dart streaming probe can preserve the
reviewed corpus contract and exceed the provisional 100 MiB/s AOT target. That
probe is test/performance infrastructure rather than the product parser. This
task promotes only the reusable UTF-8 and generated-table foundations into
`lib/`; sequence actions and terminal state mutation remain later roadmap work.

## Scope

- A public, incremental UTF-8 decoder with explicit scalar/replacement output.
- Deterministic handling of malformed starts, malformed continuations,
  overlong encodings, surrogates, out-of-range scalars, and incomplete EOF.
- Chunk- and slice-independent decoding without buffering the input chunk.
- A declarative VT state/range specification and deterministic source
  generator.
- Checked-in generated Dart tables with a stale-generation verification mode.
- Unit tests covering decoder boundaries, malformed recovery, all split points,
  table coverage, generator determinism, and generated-file freshness.

## Out of scope

- Emitting C0/ESC/CSI/OSC/DCS/APC actions.
- Parameter, intermediate-byte, string payload, or cancellation semantics.
- Grid, cursor, mode, SGR, screen, scrollback, renderer, PTY reply, or AppKit
  integration.
- Replacing or changing the reviewed Phase 0 parser corpus snapshots.
- Per-application compatibility behavior.

## Dependencies and constraints

- The core must remain pure Dart and must not import AppKit, Metal, or FFI.
- Generated tables must cover every byte value and be reproducible from a
  reviewable specification; hand-editing generated output is not permitted.
- Decoder callbacks must be synchronous, preserve byte order during malformed
  recovery, and avoid allocating an object per byte.
- Existing user or unrelated repository changes must remain untouched.

## Completion criteria

- UTF-8 scalar/replacement results are identical for one chunk, every single
  split point, bytewise chunks, and non-zero input slices.
- Valid Unicode boundaries and representative malformed forms have reviewed
  expectations and end in a reusable decoder state after `finish()`.
- The generated table has 256 byte entries per state, covers all declared
  parser states, uses valid action/next-state identifiers, and regenerates
  byte-for-byte.
- The normal project format, analysis, and unit-test checks pass, together with
  the generator freshness check.
- This note records implementation decisions, commands, results, risks, and
  handoff information; the roadmap item is checked only after verification.

## Investigation log

- The worktree was clean on `main` at `a175539` when the task started.
- The first unchecked roadmap item is the combined UTF-8 decoder/table-generator
  foundation; no later Phase 3 item may be implemented in this task.
- The Phase 0 probe already defines the required byte-order recovery behavior:
  when a non-continuation interrupts a partial sequence, emit one replacement
  and reprocess the interrupting byte. It also requires explicit EOF flushing.
- The existing package has no product VT-core module or general test framework;
  unit tests run from `test/run_tests.dart`. New focused tests will integrate
  with that entry point without adding a dependency.
- The target architecture permits `lib/src/terminal_core/` as the current
  repository-local form of the Dart-only core boundary. The implementation
  imports only `dart:typed_data`; application/platform dependencies do not flow
  into it.
- The declarative specification initially resolved to 14 states and 20 actions.
  The following parser task added one explicit malformed-header action, for 21
  actions without changing the state count. The
  generated form contains 3,584 next-state IDs, transition-action IDs, and
  explicit sequence-start flags, plus one entry/exit action pair per state.
  Values fit in `Uint8List`, and every byte is assigned through a state default plus
  validated non-overlapping local rules and validated global
  cancel/restart/C1 rules.
- The focused tests cover Unicode scalar boundaries from ASCII through
  U+10FFFF; illegal starts/continuations, overlongs, surrogates, values above
  U+10FFFF, interrupted sequences, and incomplete EOF; every single split and
  bytewise delivery of a mixed valid/malformed stream; reset/reuse and slice
  errors; all 14 × 256 generated transitions; and representative
  ESC/CSI/OSC/DCS/APC lifecycle paths.

## Decisions and alternatives

- Kept UTF-8 decoding as a small public callback-based component rather than
  using `dart:convert`. The explicit state exposes the required finish/reset
  boundary, avoids retaining chunks, and gives the future VT parser control of
  whether a byte belongs to a pending multibyte scalar or to the VT table.
- Used generated dense `Uint8List` tables for next-state and transition-action
  IDs plus state entry/exit actions. A dense `state * 256 + byte` lookup has no
  rule walk or per-byte allocation. The declarative generator remains the only
  hand-edited source of state/range behavior.
- Entry/exit actions represent OSC, DCS, and APC lifecycle without packing
  multiple effects into one transition ID. Explicit sequence-start metadata
  separates an introducer that restarts the current state from an ordinary
  self-loop. A parser applies the transition action first, then exit/entry actions on a
  state change or explicit re-entry; cancellation can therefore mark a pending
  string discarded before its exit action finalizes lifecycle.
- Included 8-bit C1 introducer transitions in the table. A pending UTF-8
  decoder takes precedence, so a continuation byte with the same numeric value
  is not interpreted as C1. This ordering is documented but execution remains
  the next roadmap task.
- Rejected promoting the Phase 0 probe wholesale: it would prematurely include
  sequence recording, limits, and dispatch semantics owned by later tasks.

## Failed attempts and corrections

- The first generator output did not parse because a trailing comma was emitted
  inside an index expression. The template was corrected before any generated
  output was accepted.
- The Dart formatter initially expanded dense list data to thousands of lines.
  The generator now emits a narrowly scoped `dart format off/on` region around
  table bytes; the surrounding generated API remains normally formatted and
  the file stays compact and deterministic.
- The first unit run found that an ASCII byte interrupting a partial multibyte
  sequence was reprocessed only as a possible UTF-8 lead and became U+FFFD.
  This was the same boundary class caught in the Phase 0 probe. The decoder now
  handles ASCII in the reprocessing loop, preserving replacement-before-ASCII
  byte order. The initial run also reported one export-order lint, which was
  corrected by sorting the library exports.

## Risks and handoff

- Parser-state actions are intentionally deferred. The generated table contract
  must be rich enough for the next roadmap task without silently implementing
  that task now.
- The next roadmap task must consume the transition action before exit/entry
  lifecycle actions, honor explicit sequence restarts, and route bytes to a
  pending UTF-8 decoder before consulting C1 table entries.
